## 0. 评估口径说明（先对齐，再开评）

### 0.1 官方规则来源

本评估以两份已在仓库内归档的官方规则提炼文档为准（均为赛题原文摘录，非二手解读）：

- `docs/赛题对照_进度盘点.md` —— 含「原创性与知识产权」「开源授权」「组队/报名」原文条款
- `docs/赛题驱动_模型清单与MediaCrawler数据利用.md` —— 含任务目标与数据红线

赛题原文对**任务形态**的硬性要求是这四件并列的事：

1. **多模态检测**（被篡改 / 拼接 / 伪造的**图文**，图片与文案并列）
2. **可解释判定**（普通人能看懂的结论，而非黑箱打分）
3. **智能体（Agent）**（会自己判断下一步查什么）
4. **通过数据集展示闭环**（用数据证明有效）

### 0.2 关于"评分标准"的重要诚实声明

⚠️ **仓库内未检索到天池官方的量化评分细则**（初赛/复赛/决赛权重、各维度分值）。我们只掌握赛题原文的任务要求，以及自己三份设计文档（方案 A/B/C）附录里**自行归纳**的 6 个评审维度（创意性/商业前景、技术难度、完成度、运行速度、社会价值、AI 合规性）。

→ 因此第 4 节"获奖概率"是基于**任务契合度 + 工程完成度 + 可见硬伤**做的判断，不是按官方记分表算出来的。**补齐官方评分细则是 P1 必做项（见第 5 节）。**

### 0.3 "b+c 方案"的解读

三份设计文档：方案 A=质检流水线（Streamlit）、方案 B=多 Agent 圆桌协作（FastAPI+SSE，orchestrator+3 个专项 Agent+judge）、方案 C=流水线 + LLM 解释层（Qwen2.5-7B + Validator 护栏）。

本仓库实际落地的形态 = **方案 C 的流水线骨架 + 方案 B 的 Agent 调度脑子 + 方案 C 的解释/护栏层**，即「b+c」= **B 的智能体编排 + C 的可解释/护栏**。本评估按此解读展开。若你心中"b+c"另有所指，请即时纠正。

## 2. b+c 方案实现进度

### 2.1 已完成（✅）

- **方案 C · 取证流水线**：`pipeline.py` 把 8 个工具串成统一证据链 → `rule_engine.py` 四档定级（high_risk / suspicious / credible / inconclusive）→ JSON + Markdown 报告。
- **方案 C · 本域 AIGC 微调模型**：`models/beautyproof_aigen_v2/`（timm MobileNetV3-Large，ImageNet 预训练，~17MB）。实测：真实美妆图误报 66.2%→1.4%，AI 召回 100%（即梦域）。v1 保留作兜底，回滚只删一项。
- **方案 C · 可解释报告** + **方案 C · 护栏**：`report_generator.py` + `validator.py`（六道关）。
- **方案 B · Agent 调度脑子**：`planner.py`（波次 + 可解释跳过 + 后置动作），是整条流水线的"灵魂"，也是答辩最该讲的故事。
- **双形态交付**：`web/app.py`（Flask 5000 本地演示）+ `demo/index.html`（离线自包含）+ 线上 `https://beautyproof-demo.app.workbuddy.host/`（已验证 HTTP 200，含 ai_17 / 高风险 / TruFor 定位图）。

### 2.2 未完（❌ / ⚠️）

- **方案 C · 真·LLM 解释层（核心缺口）**：设计文档写的是 Qwen2.5-7B 出"人话解释"。仓库里只有一个 `download_vlm.py`（下载 Qwen3-VL-4B-Instruct-GGUF，4B、Q4_K_M 约 2.5GB、Apache-2.0 可商用、纯 CPU 可跑），**但从未接入 pipeline**。当前报告是模板拼装 + 规则，不是大模型生成。这是"可解释判定"这条官方要求里最弱的一环。
- **方案 B · 多 Agent 圆桌**（orchestrator + ImageAgent + TextAgent + SourceAgent + JudgeAgent，FastAPI+SSE）：**未实现**。实际用单一 `planner.py` 替代。功能上够用，但少了"多角色交叉验证/辩论"的视觉冲击，答辩时少一个记忆点。
- **数据集规模 & 跨生成器**：见 1.4。受控集仅 35→74 张；跨生成器 25%。

### 2.3 进度百分比

**b+c 主线完成度 ≈ 78%**：流水线 + Agent 调度 + 护栏 + 双形态交付都齐了；差的 22% 主要是"真 LLM 解释层"和"多 Agent 圆桌"两件事，以及数据集泛化补强。

## 3. 技术水平与代码质量

### 3.1 亮点（答辩该重点讲）

- **统一证据格式**：8 工具共享一套 `{tool, observed, cannot_prove, evidence[]}`，可组合、可审计，工程素养明显高于"各跑各的脚本"。
- **可解释 Agent 是真做的**：`planner.py` 的 R1–R5 不是装饰，每条跳过都带人话理由，直接命中赛题"可解释"+"Agent"两个关键词。
- **本域微调是差异化杀招**：通用开源 AIGC 检测器（AIRealNet/capcheck）在中文美妆域集体失效，本团队用 74 张真实精修美妆图 + 20 张即梦图微调出 v2，把误报从 66% 压到 1.4%——这是"针对美妆场景定制"的硬证据。
- **双模型互补定位清晰**：TruFor 管"被局部人工改过"，AIGC 管"整张 AI 画的"，口径不打架（R5 规则专门处理）。
- **交付形态完整**：CLI / 本地 Web / 离线 HTML / 线上 Demo 四选一，评委怎么看都行。

### 3.2 短板（别回避，评委必问）

- **解释层不是真 LLM**：这是方案 C 的设计核心，现在落空。会被问"你的可解释到底是不是大模型生成的"。
- **跨生成器泛化差**：v2 在即梦域饱和，换 MJ/SD/Flux 只剩 25% 召回。规模小 + 单生成器训练是根因。
- **TruFor 许可证灰区**：CVPR2023 开源代码直接 `setup_trufor.py` 拉进仓库依赖，但没声明许可证/归属 → 踩原创性红线风险。
- **无测试 / 无 CI / 无依赖锁**：55 个 py 文件但缺 `requirements.txt` 精确 pin、缺单测；评委或复现者环境不一致会跑不起来。
- **工程"完成度"高于"算法新颖度"**：方法是成熟组件组合，没有自研新模型/新损失——创意性维度不占优。

### 3.3 技术评级

**中上（B+）**：工程完整度、场景贴合度、可解释设计是强项；算法原创性、规模、泛化是弱项。

## 4. 获奖可能性与竞争优势

### 4.1 竞争优势

1. **最贴赛题**：多模态 + Agent + 可解释 + 数据集闭环，四条全中，且"可解释 Agent 调度"讲得通。
2. **真能跑的闭环**：不是 PPT 概念，线上 Demo + 受控评测 100% + 真实误报压到 1.4%，可信度高。
3. **行业落地感强**：紧扣美妆"种草文/评论区/AI 素材"真实痛点，商业叙事顺。
4. **本域微调亮点**：直接回应"通用模型在我们领域不准"这个评委最爱看的对比。

### 4.2 关键短板（按致命度排序）

1. **合规硬伤**：private 仓库 + 无 LICENSE + TruFor 未声明许可证 → 可能被直接判"不符合原创性/IP 要求"。
2. **解释层空壳**：方案 C 核心（LLM 解释）没落地，答辩会被追问。
3. **跨生成器 gap**：25% 召回，答辩必被问"换生成器还灵吗"。
4. **缺官方评分细则**：不知道评委真按什么打分，准备容易跑偏。
5. **缺演示视频 + 答辩 PPT**：零产出，临场靠口述吃亏。
6. **数据集规模小**：35→74 张，统计说服力有限。

### 4.3 获奖概率判断（分档）

- **当前状态（不补）**：完成度 ~75%，但合规硬伤 + 解释层空壳两件事会卡评审。**初赛过关概率中等，冲决赛概率低（≈20–30%）。**
- **补完 P0（合规 + 真 LLM 解释层）**：消除资格风险 + 补全方案 C 核心。**冲决赛概率升至中等偏上（≈45–55%）。**
- **再补 P1（官方细则对齐 + 视频 + PPT + 跨生成器 v3）**：**决赛获奖概率 ≈ 60–70%**，具备争冠相。

> 一句话：**现在的项目"像能拿奖的样子"，但还差最后两块拼图（合规 + 真解释层）和一层包装（视频/PPT/细则对齐）。补上就是强竞争者，不补容易止步初赛。**

## 8. 官方评审准则对齐（Brandstorm 2026 · 2026-09-25 补充）

### 8.1 找到的官方口径（关键补证）

此前 §0.2 诚实声明"仓库内未检索到官方量化评分细则"。经 WebSearch 核实，**欧莱雅 Brandstorm 2026 全球赛官方评审 = 项目 25 分 + 团队 25 分 = 50 分**，每项按 Strongly observed(5) / Observed(2) / Not observed(0) 三档给分：

- **项目维度（25）**：INNOVATIVE · SUSTAINABLE · INCLUSIVE · FEASIBLE · SCALABLE
- **团队维度（25）**：JUDGMENT · RESILIENCE · AMBITION · EMPATHY · LEARNING AGILITY

⚠️ **双轨提醒**：天池赛题 532496 技术赛道另有"多模态 / 可解释 / Agent / 数据集闭环"的任务验收口径（见 §1），但 L'Oréal 评委**最终打分遵循上述 5+5**。答辩与 PPT 必须同时覆盖"技术验收"与"5+5 商业/团队叙事"两层——纯技术讲法会丢团队维度的 25 分。

### 8.2 BeautyProof 逐条映射

| 维度 | 官方含义 | BeautyProof 对应证据 | 自评档位 |

## 9. v3 跨生成器重训结果（2026-09-25 末）

用户要求"把 25% 跨生成器召回拉起来"，已完成并实测：

- **做法**：新增 `data/ai_cross/`（非即梦 / ImageGen 风格 AI 美妆图，含先前自产 8 张 + 本轮新生成 18 张，共 26 张）；`tools/train_aigen_v3.py` 把 `ai_cross` **单独划分、只把训练份并入 AI 类、验证份整体留作干净 held-out**，确保跨生成器指标不被训练污染。真实类不变（real_xhs 74 + 原有 15）。
- **结果**：最佳轮 = 9（早停），验证集混淆 TP=9/FN=0/FP=1/TN=17，**整体 val_acc = 0.963**；**跨生成器 held-out 召回 = 5/5 = 100%**（v2 基线仅 25%）。训练耗时 ~407s（CPU）。
- **代价**：真实类验证集误报较 v2（1.4%）略升（本验证批 1/18 ≈ 5.6%），属"为跨生成器多样性付出的微小代价"，整体仍可控。
- **上线**：`aigc_tool.py` 的 `MODEL_PRIORITY` 首位改 `beautyproof_aigen_v3`，v2 保留第二位兜底（回滚只删一项）；v3 权重已入仓（gitignore 已 `!models/beautyproof_aigen_v3/`）。
- **诚实边界仍在**：held-out 验证用的是 ImageGen 风格图（与训练份同生成器不同提示），**并未覆盖 MJ/SD/Flux 真·第三方生成器**。若用户能提供 MJ/SD/Flux 美妆图放入 `data/ai_cross/` 重跑，可把"跨生成器"从"跨提示"推进到"跨生成器内核"。

**修订后竞争力结论**：技术维度（含跨生成器泛化）短板已补齐 → 决赛入围概率维持 **≈65–75%**；剩余唯一硬约束 = 团队 5 项叙事需 owner/队友口述补实（EMPATHY/AMBITION）。
